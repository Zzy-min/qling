## 1. Headless / ACP

### Grok Build
- `crates/codegen/xai-acp-lib/`（2.4k 行）：传输层。
  - `src/stdin_reader.rs`：专用线程阻塞读 stdin。Windows 上把真实 stdin 复制成私有句柄，再把进程 stdin 指向 `NUL`，防止其他代码误读 stdin 导致会话卡死（模块注释记录了 `session/new` 卡死案例）。通道深度很小，借此形成背压。逐行经过 `normalize_json_line`，兼容 `\/` 转义的 method。
  - `src/line_reader.rs` `LineBufferedRead`：只按完整行交付，解决 `read_line` 在 `select!` 中取消不安全的问题；`MAX_LINE_SIZE = 64 MiB`，防止对端不发换行导致内存无限增长。
  - `gateway.rs` / `channel.rs`：agent 侧与 client 侧双向消息网关。
- `crates/codegen/xai-grok-pager/src/app/acp_handler/`（7k 行）：客户端处理。
  - `queue.rs`：prompt 排队与 FIFO 交接（`pending_running_adoptions`），处理多客户端排队。
  - `prompt_origin.rs`：`x.ai/session/prompt_complete` 轮末信号，带 `promptId`（修复"响应丢失"）、取消原因（`HookDenied` 时附 hook 名与原因）；可区分自动唤醒轮（后台任务/子 agent 完成）与 `/loop` 定时轮。
  - `permissions.rs`、`subagent_lifecycle.rs`、`session_notification.rs`（2k 行，流式更新）。

### qling 现状
- `src/cli/acp-server.ts`（297 行，基于 `@agentclientprotocol/sdk`）：支持 initialize / authenticate / session.new / setMode / prompt / cancel；approval 走 `requestPermission`；工具事件映射成 `tool_call` / `tool_call_update`。
  - `agentCapabilities: { loadSession: false }`（约第 154 行）：qling 本身有 `restoreSession` 和 interrupted-run，但 ACP 不能恢复会话。
  - `prompt()`（第 207 行起）：`await session.agent.run()` 结束后才**一次性**发送一个 `agent_message_chunk`，没有流式输出；`index.ts:1088` 注释也写明"Headless, Mission and ACP remain complete-response by default"。
  - 同一会话已有 prompt 在跑时直接 `throw`（第 209 行），不排队。
  - `forwardExecutionEvent` 只转发 tool_started / completed，不发 plan / todo、usage，也不带工具参数和输出摘要（`rawInput` / `content`）。
  - `newSession` 拒绝 client 提供的 MCP servers 和 additionalDirectories（明确报错，合理）。
  - `sessions` Map 只在 shutdown 时清空，没有 session 关闭和空闲回收（长时间运行的 IDE 客户端会持续累积 AgentLoop）。
  - stdout 保护：对 `agent-loop.ts` / `agent/*` / `tools/*` / `pipeline/*` / `mcp/*` / `session/*` 做 rg，没有发现 `console.log`（✔）。但运行时没有守卫：第三方依赖一旦写 stdout，就会污染 NDJSON。
- `src/cli/headless-json.ts`：`HEADLESS_JSON_SCHEMA_VERSION = 1`，结果中带 outcome、recovery、usage ✔。

### 书本清单

## 2. Goal / loop 自主运行

### Grok Build（`crates/codegen/xai-grok-shell/src/session/`，goal_* 共约 1.7 万行）
- `goal_tracker.rs`：纯状态机。`GoalStatus` 有 Active / UserPaused / BackOffPaused / NoProgressPaused / InfraPaused / Blocked / BudgetLimited / Complete。**未知或损坏的状态值反序列化为 UserPaused**（文件头注释："a corrupt or forward-version snapshot can never resurrect as a self-driving goal"）。`GOAL_CLASSIFIER_STALL_THRESHOLD = 2`；`GOAL_HISTORY_MAX = 64`。
- `goal_classifier.rs`：验证由 N 个怀疑者子 agent 并行反驳（`GOAL_VERIFIER_SKEPTIC_COUNT = 3`，范围 1–5），不经过 task 工具，主 transcript 保持干净。结果分三类：`Achieved` / `NotAchieved{gaps_summary, gap_fingerprint}` / `Blocked`（全部是环境或矛盾类缺口，迭代无用，转人工）。`gap_fingerprint`（约第 995 行）对缺口证据中的路径和行号做归一化；同一指纹连续出现 2 次，判定"无进展"并自动暂停。`GOAL_CLASSIFIER_MAX_RUNS_DEFAULT = 10`。
- `goal_planner.rs`：失败即暂停（fail-closed）；`goal_strategist.rs`：尽力而为（fail-open），连续 N 次未达成后提出结构性调整，只写 strategy note，并用 `PlanGuard` 快照保护 plan.md；`strategist_should_fire(consecutive, last_fired, every)`。
- `goal_stop_detector.rs`：取最后一个非空段落，用正则判断"过早放弃"：unable_to_proceed / giving_up / stopping_here / agents_in_flight / check_back_later（"等你"之类不算）/ commit_push_pr / ready_for_review / please_deflection 等。命中后换用专门的催促文本，并发 `GoalPrematureStopDetected{pattern}` 事件，用于审计正则的准确率。
- `xai-grok-session-events/src/types.rs`：GoalClassifierFired / Verdict / FailOpen / FailClosed / CapReached、GoalStrategist*、GoalAutoPaused、TodoGateFired / Exhausted 等事件全部落到 events.jsonl。

### qling 现状
- `src/session/goal-controller.ts`（168 行）`afterTurn`：
  - 只有自动轮数上限 `QLING_GOAL_MAX_AUTO_TURNS = 12`；**没有停滞检测**——评估器每轮给出相同原因时也会耗满 12 轮。
  - 超过上限时：除非开启 `QLING_FEATURES_EVIDENCE_GOALS`，否则 `clearGoal`，目标直接丢失，不可恢复（Grok 是 BudgetLimited，可恢复）。
  - 有 `outcomeContract` 时走证据判定（`outcome-evidence.ts`）✔；否则调用 LLM 评估器。
  - `messagesToTranscript` 取最后 40 条消息，直接 `${content}` 拼接（非字符串内容可能变成 `[object Object]`，需 Pi 核实 Message.content 的类型）。
- `src/session/goal-evaluator.ts`：
  - 缺 key 或结果无法解析 → `done:false`，并把原始文本当作 reason 继续推进——**评估器坏了，目标照样空转**。
  - `fetch` 出错或超时会直接抛出（`evaluate` 只有 `try/finally`，没有 catch）。
- 调用方：`src/tui/streaming-repl.ts:515` 的 `afterTurn` 在 `try/catch`（505 行结束）之外，评估器网络异常会直接冒出 goal 循环；`agent/durable-session-supervisor.ts:156` 同样没有 catch。
- `src/session/session-goal-manager.ts`：
  - `loadGoal`（约 195 行）直接 `JSON.parse`，不校验 status，未知值原样保留；
  - `saveGoal` 用 `fs.writeFile` 直写——**没有使用已有的 `persistence/atomic-json.ts`**；
  - 状态只有 active / achieved / blocked / canceled / cleared，没有 paused 一族。
- 过早放弃检测：rg `premature|放弃|giving up` 在 session/ 下无结果 ✘。
- `src/session/session-scheduler.ts`：loop 任务有指数退避（1s→60s，连续失败 4 次转 failed）、busy 时置 pending、写盘用 tmp+rename ✔，质量不错。

### 书本清单
- §7.4.2 验证器"核实机器可独立复核的事实，而非 Agent 的自我陈述"：qling 的 outcomeContract 路径 ✔；LLM 评估路径只读最后 12k 字符的 transcript，属于"自我陈述"判定 ～。
- §9.3.1"完成≠进步、保留负面结果"：没有缺口指纹和历史，无法识别反复原地踏步 ✘。
- §5.1.5 控制流层"死循环 / 连续失败计数 / 熔断"：goal 循环只有轮数上限 ✘；评估器故障后的 fail-open / fail-closed 策略没有显式定义 ✘。

### 可借鉴

## 3. Hooks 进阶 + 信任

### Grok Build
- `xai-grok-hooks/src/event.rs`：`MAX_PAYLOAD_SIZE = 128 KiB` + `truncate_payload`；`MAX_HOOK_FEEDBACK_CHARS = 10_000`；Stop 的 payload 带 `stop_hook_active`（第 432 行），供 hook 判断自己是否正在拦截链中。
- `src/config.rs` `HookSpec`：name / event / `configured_matcher` + 编译后的 `matcher` / `enabled` / `timeout_ms` / source（File / config tier / Plugin）/ `command_raw`（显示用，不泄露展开后的密钥）。
- `src/dispatcher.rs` `StopDispatchResult`：`blocks`（阻止停止并给出原因）、`prevent_continuation`（强制停止）、`wants_continuation()`、`feedback()`（逐条截断）。
- `xai-grok-shell/src/session/acp_session_impl/stop_gate.rs`：`MAX_STOP_HOOK_CONTINUATIONS_PER_TURN = 8`，达到上限时提示并结束该轮——防止 Stop hook 造成死循环。
- `src/trust.rs`：`Trust::allows_project_sources()`——**项目级 hooks 和插件只在受信工作区加载**；`DisabledHooks`（`$GROK_HOME/disabled-hooks` 按名称逐行，`#` 为注释）；`allow_managed_hooks_only`；`skip_reason` 区分 UserDisabled / ManagedOnly。
- `src/matcher.rs` 用正则匹配工具名。

### qling 现状
- `src/hooks/json-hooks.ts`（224 行）：7 个事件（新增 SubagentStart/Stop）；仍然**没有 matcher、没有 stdin payload 上限、没有 Stop / UserPromptSubmit / PreCompact、没有 name/enabled、没有禁用名单**；全局开关 `QLING_JSON_HOOKS_ENABLED`；manifest 只有一个来源（stateDir 或 env），不读项目级 hooks——因此**项目 hooks 暂时没有信任问题**。
- `HookResult.preventContinuation`（types.ts）已存在，但 JSON hook 无法在轮末使用。
- 工作区信任：
  - `src/tools/skill.ts:63-84` `getSkillDirs()`：**cwd 下的 `skills/`、`.qling/skills`、`.grok/skills`、`.claude/skills|commands`、`.cursor/skills`、`.agents/skills` 无条件加载，且优先级高于用户目录（"先出现优先"），同名时会覆盖用户 skill**。有 `skills/security-scan.ts` 内容扫描兜底，但没有"是否信任此目录"的概念。
  - `src/agents/role-loader.ts:104` 加载 `<workspace>/.qling/agents`（allowed_tools 与内置角色取交集，风险有限）。
  - 插件：`src/plugins/local-installer.ts` 需要签名或 `--allow-unsigned` ✔；`discovery-registry.ts:113` 带 `requireSignature` ✔——插件信任门已基本具备，强于工作区 skill。
- 对比 Grok：信任粒度是"工作区"，qling 目前只有"插件签名"这一层。

### 书本清单
- §9.3.2"提示注入若被总结成经验，可能跨会话反复生效 / 恶意包封装成工具会扩散"：不受信仓库的 skill 覆盖同名用户 skill，正是这类供应链注入面 ✘。
- §2.5.3 / §4.4.3：skill 正文按需加载，降低了暴露面，但目录描述本身也会进入系统提示。
